# Development Principles

本文档记录 SYNC-THINK 项目级开发原则。它补充 `AI_DEVELOPMENT_RULES.md`。  
产品 Locked 决策与完整系统边界见：`docs/superpowers/specs/2026-07-11-sync-think-product-design.md`。

## 1. 产品原则

1. **上下文连续性优先于自动化。** 应用拥有任务状态真源；模型会话不是真源。
2. **用户控制模型路由。** 系统不静默替换模型；无成本驱动换模。
3. **渐进编排。** 默认单 Agent 多轮对话；协作/自动在同一任务内按需升级。
4. **Local-first。** 首版密钥、任务状态、工具执行、产物均本地。
5. **可检查。** 每次模型调用、工具动作、审批、上下文转移、记忆变更可追溯。
6. **默认安全。** Runtime 侧策略强制；完全访问由用户显式选择并全自动执行，其他模式对敏感操作保持门禁。
7. **聊天是主体验。** 图、轨迹、审批、上下文详情按需展开。
8. **定义版本化。** Agent/Skill/Workflow/Policy 变更不改写历史 Run。
9. **禁止重开 Locked 决策**，除非用户给出新需求。
10. **闭测边界明确。** 不实现 Later 列表（订阅登录、团队云、跨平台发布、公开市场等）。

## 2. 技术原则

1. 优先实现清晰、稳定、可维护的方案。
2. 不为短期演示牺牲核心业务正确性（尤其是恢复、权限、上下文完整性）。
3. 不引入没有明确收益的复杂架构；首版是**模块化单体**，不是微服务。
4. 新增能力必须能被后续开发者理解、测试和维护。
5. 设计阶段必须提前考虑性能影响，而不是实现完成后再补救。
6. 前端默认考虑按需加载、按需引入、避免无意义重渲染、避免一次性加载过大资源。
7. Runtime 默认考虑分页/增量事件、超时、重试边界、连接复用与背压。
8. 任何可能明显影响性能的技术选型，都必须记录在 `engineering/04-tech-decisions.md`。
9. 涉及核心技术选型、重大依赖、架构变化或第三方服务时，必须先给出 2-3 个方案并等待用户确认，不能由 AI 直接拍板。
10. UI 重启不得终止活跃 Run；Runtime 可被未来 CLI/本地 runner 复用。
11. Provider 适配器边界清晰：OpenAI-compatible 与 Anthropic-compatible 显式实现；其他协议后续扩展。
12. 外部副作用前必须先持久化意图/事件；检查点在每个可观察转换后写入。

## 3. 代码组织原则

```text
前端目录约定（规划）：
  apps/desktop/          Electron shell + React UI
  packages/ui/           可复用 UI 组件与 token
  packages/shared/       跨进程共享类型、协议、错误码

Runtime 目录约定（规划）：
  apps/runtime/          独立 Node/TypeScript Agent Runtime
  packages/core/         编排、状态机、上下文编译、策略
  packages/adapters/     Provider 适配器
  packages/workers/      文件/终端/浏览器/桌面/媒体/MCP worker 接口与实现

公共模块约定：
  packages/protocol/     UI ↔ Runtime 本地协议与鉴权
  packages/storage/      SQLite、artifact store、迁移
  packages/security/     凭证引用、路径规范化、策略评估

配置文件约定：
  本地用户数据目录可配置；密钥不进仓库；环境示例用 .env.example

测试目录约定：
  与包同树或 packages/*/tests；合同测试夹具单独维护
```

最终目录以 `docs/engineering/11-project-structure.md`（待 scaffold 后填充）为准。

## 4. UI/交互原则

具体前端设计方向以 `docs/product/15-frontend-design.md` 与 tokens 为准。

```text
整体风格：可获奖级精密工作台（Continuum Bench）；完整浅/深主题；无分裂主题
布局原则：左文件夹任务树 / 中完整聊天 / 右可折叠轨迹（IA Locked；视觉原创）
组件原则：基础组件原创；Context Continuum 为签名元素；禁止组件库默认皮肤直接上
表单原则：导入与危险配置必须预览+确认；内联错误
错误提示原则：可行动、分类清晰、可打开脱敏诊断
Windows 适配要求：高 DPI、缩放、键盘导航、对比度、reduced-motion
设计质量：每个主页面至少一个有意义记忆点；动效可感知但必须服务状态理解
```


必须明确：

1. 产品形态为 Windows Electron 桌面端。
2. UI 风格参考 V3 结构 + Linear/Codex 气质。
3. 色彩/布局/组件以 tokens 与前端设计文档为准。
4. loading / empty / error / success / disabled / focus 状态齐全。
5. 禁止装饰性动效与营销页风格。
6. 执行图、编辑器、诊断等重型面板按需加载。

## 5. API 原则

首版主要是 **UI ↔ Runtime 本地协议**，不是公网 HTTP API。

```text
接口命名：命令/查询分离；命令带 expected task/version 以支持乐观并发
请求格式：类型化消息（TypeScript 共享类型）；禁止 Renderer 直连 Node
响应格式：事件流 + 查询快照；长操作可订阅
错误格式：稳定错误码 + 用户可行动消息 + 脱敏诊断引用
分页规则：消息、事件、产物、诊断默认分页/增量
鉴权规则：仅当前 OS 用户可连接；校验安装身份；密钥永不进 Renderer 状态
```

Provider 出站调用：

- 通过 Runtime 适配器；密钥从安全存储取用后仅在内存短时使用
- 归一化流式事件；保留 secret-scrubbed 原始证据用于诊断

## 6. 数据原则

```text
数据模型原则：
  - SQLite 为真源
  - 定义与历史版本化
  - 搜索索引是派生数据
  - 事件追加式；检查点可重建状态

唯一性约束：
  - Workspace/Task/Run/Step/ArtifactVersion 稳定 ID
  - Step ID 跨重试与恢复保持稳定

删除策略：
  - 软删除优先；不可逆删除属人类专属动作
  - Artifact 版本不可原地覆盖

审计字段：
  - 每个模型变更、审批、工具调用、记忆变更、产物、凭证引用可审计

数据备份：
  - DB 迁移前先备份
  - 迁移失败回滚并进入只读诊断模式
```

## 7. 安全原则

1. 密钥、token、密码不得写入代码仓库、Renderer 状态、提示词、日志、诊断导出、团队同步。
2. 权限校验在 Runtime 侧强制；前端展示不能替代授权。
3. 错误信息不能暴露敏感数据与明文密钥。
4. 用户输入、网页、文件、工具输出均为不可信数据，不可自我提升为高优先级指令。
5. Electron Renderer 无 Node 直达；contextIsolation + 严格 CSP。
6. 路径必须规范化并校验授权根目录。
7. Worker 仅接收最小能力令牌与作用域工作目录，不接收无关凭证。
8. Skill/MCP 版本新增工具或权限必须重新审批。
9. 敏感操作在请求批准、替我审批和自定义模式下不能由审批 Agent 越权；完全访问直接执行但必须保留审计。
10. 禁止非官方 Cookie / token / 未文档化鉴权文件提取。

## 8. 质量原则

```text
必须运行的检查：
  - typecheck
  - unit（状态机、权限、上下文编译、路由、回退链）
  - 相关 contract / integration
  - build

必须覆盖的测试：
  - 编排状态机与恢复
  - 权限与人类专属门禁
  - Provider 流式合同夹具
  - Context Packet/Manifest
  - 路径穿越 / 命令注入 / 提示注入 / 密钥泄漏安全用例

可接受的技术债：
  - Phase 0 假 Provider
  - 视觉品牌 refinement 延后到 Phase 0/3
  - 部分 Worker 可先接口后实现（但不得假装已完成闭测验收）

不可接受的技术债：
  - 明文密钥
  - 无检查点的外部副作用
  - 静默换模型
  - last-write-wins 并行产物
  - 可绕过的人类专属动作
  - UI 生命周期绑定导致 Run 中断
```

完成需求后，最终回复必须包含可直接执行的验证步骤；桌面 UI 变更需说明窗口操作路径。

## 9. 性能设计原则

每个新增功能在设计或实现前，必须考虑：

1. 是否会增加首屏/主窗口加载体积。
2. 是否可以按需加载执行图、Context inspector、诊断、重型预览。
3. 是否可以按需引入第三方库，避免整包引入。
4. 是否会造成重复请求、瀑布请求或过大的协议消息。
5. 长对话、轨迹事件、日志是否需要虚拟化、分页或增量加载。
6. 是否需要缓存、去抖、节流或后台任务。
7. SQLite 查询是否有索引、是否会大事务阻塞 Runtime。
8. 是否需要监控关键耗时、错误率或资源使用。

性能优化不是无条件复杂化。只有当收益明确或风险明显时才引入额外机制，并在技术决策中说明取舍。

## 10. 技术选型门禁

以下事项必须先进入方案推荐，等待用户确认后才能实施：

1. 选择或更换前端/后端框架、Electron/Runtime 边界实现。
2. 引入数据库驱动、迁移框架、缓存、队列、对象存储、搜索服务。
3. 引入鉴权、支付、邮件、短信、推送、第三方登录服务。
4. 引入图表、富文本、地图、表格、文件预览等重型前端库。
5. 调整部署/分发、CI/CD、签名、更新、监控、日志方案。
6. 新增会明显影响包体积、性能、成本、安全或维护复杂度的依赖。
7. 第 24 节技术 spike 中尚未锁定的具体库选择。

方案推荐必须包含：

```text
技术需求：
约束条件：
方案 A：
方案 B：
方案 C：
推荐方案：
推荐理由：
性能影响：
维护成本：
风险与回退：
需要用户确认的问题：
```

## 11. 恢复与编排原则

1. 先持久化意图/事件，再调用外部副作用。
2. 每个 Run/Step 有稳定 ID 与幂等标记。
3. 仅对已分类的瞬时失败重试，且有上限。
4. 认证失败、协议不兼容、权限拒绝、验收拒绝不得当网络错误重试。
5. Worker 崩溃只失败其 Step，并标记部分产物不完整。
6. 上下文溢出产生可见压缩提案；目标、决定、验收标准不得被静默删除。
7. 计划一旦 Run 开始即不可变；编辑生成新计划修订与可审计 diff。

## 12. 文档与实现顺序

1. 先文档/决策，再实现。
2. Runtime、状态、权限、适配器、恢复相关能力优先测试先行。
3. 不实现闭测非目标来“顺手做”。
4. 变更行为必须更新 changelog / 相关 docs。
