# Grok Bot 协作对齐：证据、现状与改造规格

日期：2026-10-01（Asia/Shanghai）
状态：原始调研与提案；其中「群内通信权限拆分、确定性路由、咨询后原任务续做、可见投递状态」已于同日实现。实施边界见 ADR 0004 的 2026-10-01 amendment 和测试指南；其余方案仍是提案。

## 1. 结论

参考 Grok Bot 的持久 Bot 身份、真实异步通信、群内可见交接与按职责持有上下文。保留用户明确要求的「一个长期任务一个群」「重复邀请同一小队」「同一成员参与多个群」。小队是成员配置，群是任务空间，两者不合并。

「严格参考」应以公开行为与实证接口为边界，不猜测闭源服务端实现；对外介绍的 Team Bots 与我们已有的小队执行器也要区分。

## 2. 证据分级

### 官方已说明的行为

- S1：Bot 可异步联络另一 Bot，接收者被唤醒并可稍后回复；群消息可定向 @，也可由参与者决定回应。交接在对话中可见。
- S2：Bot 可以保留角色相关的稳定信息与摘要；变化中的事实仍应回到权威来源核对。
- S3：发布介绍支持多 Bot 并行、相互联络和群内协作；这不是服务端调度算法的公开实现。
- S4：官方设计文章区分可共享的能力与角色相关的记忆，群提供项目共享上下文；协调者承担常规路由，而非让用户操作每次交接。
- S5：Team Bot 是供组织成员使用的同一个 Bot；共享配置/团队记忆与个人会话、个人笔记分开。
- S6/S7：共享计算机文件可用于交接；账号下各 Bot 并非文件或凭据的安全隔离边界。

以上是产品契约。我们不从这些内容推导其服务端使用何种数据库、投递保障或精确的上下文压缩阈值。

## 3. 对照当前 SYNC-THINK

已具备的能力应保留，不再重复建设：

- 独立任务群及小队成员快照、持久消息/任务/尝试/检查点。
- 群内消息工具、关联私聊工具、独立任务派发工具；发送身份由运行时绑定。
- 本群有限上下文、分页回读、产物版本与恢复；不是把所有历史无限塞入 prompt。
- 任务群切换不暂停运行，重复邀请会创建不同群。

具体差距：

1. **群内对等通信和另开私聊被同一权限控制。** `CollaborationChatService.recipients` 用 `allowPeerDirect` 拦截非协调员之间的群内通信；`sendPeerDirectMessage` 又用它控制关联私聊。两个行为应分开。
2. **没有指定接收者时固定进入协调员。** `recipients` 的默认目标为 `coordinatorMemberId`。这是当前策略，不是 Grok Bot 文档中的参与者选择回应机制。
3. **用户输入、群内转交、任务派发缺少清晰的统一表现。** 现有工具是真实工具，但需要让人一眼看出是谁联系谁、为何联系、属于哪个任务、现在是等待还是完成；不再用一句「已经通知」代替真实投递状态。
4. **跨 Bot 联系目前限定为同一父群的活跃成员。** Host 验证双方成员关系并引用原消息。这是有用的隔离约束；跨群协作应新增显式分享范围，不是直接放开所有历史。
5. **协调/执行角色限制与更自由的成员协商存在边界冲突。** ADR 0004 允许负责人派工、工作成员不再派工。可以先放开有边界的咨询交接；改变工作所有权或允许成员再派工时须明确修订 ADR 与迁移，不静默扩大权限。

## 4. 拟采用的实现规格（本项目设计，不冒充 Grok 服务端源码）

### 4.1 四个对象

- Bot：可复用身份、角色、技能与工具配置。
- Squad：方便邀请的一组 Bot 与默认分工，不占据唯一会话。
- Room：一个目标的讨论、决策、文件、任务、检查点及成员权限。
- Work item：确定要完成的产出及验收，挂在 Room 下，可在群里交接负责人。

### 4.2 通信与执行分开

同群消息、Bot 定向联络、工作交接是三种命令，共用持久消息记录和关联标识，而不是三套互不相认的执行体系。

建议消息信封保存消息 ID、幂等键、发送身份、接收身份、所属群、引用消息、相关任务、回传地址、是否需要回应及授权上下文引用。身份和可读范围均由 Host 校验，模型不自填全局执行身份。

送达、排队、处理中、等待回复、完成、失败是不同事实。持久投递可重试，副作用由幂等与执行记录尽量抑制重复；不承诺任意外部操作 exactly-once。

### 4.3 群内路由

明确 @ 优先；回复消息继承交接关系；无明确接收者时先识别当前负责人/待答事项，确有必要再选其他成员。协调员是可配置的默认负责人，不是每句对话都必须经过的中转站。

参与者可主动提出有因果来源的咨询，回复结果仍回到原任务。确认、感谢、状态广播默认不唤醒下一轮。保留次数、预算、期限与用户停止控制；减少无意义自动往返，而非一律禁掉成员沟通。

### 4.4 小队与小队协作

同一项目：邀请多个小队/临时专家进入同一个群，由真实 Bot 身份沟通；一个阶段只保留一个负责人。

不同项目：默认隔离。如确实需要协作，发送明确的交接包（目的、问题、允许分享的摘要、产物引用、接收方、回传群）；不得继承另一群完整历史和写入范围。全局 Bot 身份相同不代表会话上下文相同。

### 4.5 上下文与记忆

- Bot 层：通用专业知识、稳定偏好、批准复用的技能。
- Room 层：这本书的人物、世界观、确认决定、任务进展与文件。
- Turn 层：这次触发、新信息、引用内容及必要历史。

加入新成员：给本群目标、成员/职责、决定摘要和产物索引；支持按需回读，并记录实际读过的范围。移出成员：阻止新的投递与工具读取，已有执行的收尾须有明确策略。

跨群复用知识必须显式提升/分享，不把小说 A 的剧情自动写进全局 Bot 记忆影响小说 B。现有应用级目录隔离继续保留，不宣称它等同 OS 沙箱。

### 4.6 交互与设置收敛

保留群聊界面、小队邀请、独立长期任务和用户的「先讨论，再开始工作」。工作授权是清晰的确认点，不要求用户先编排完整 DAG。后端仍保留可靠任务状态机。

普通设置聚焦群内协作、是否允许关联/跨群联系、自动运行预算和何时需用户决定。深度/节点/执行次数等低层约束移至高级或诊断区域，避免多个相似开关互相覆盖。旧策略显式迁移，现有禁止状态不悄悄变为允许。

Grok 官方以持久 Bot 为产品主体；本项目同时保留独立任务群入口，是为了满足同一小队并行写两本书的既定需求，不照搬「每 Bot 一个入口」后重新隐藏任务群。

## 5. 实施顺序与验收

1. 分离群内通信、关联私聊、跨群交接策略，统一消息因果关联和投递状态；保持旧数据可读。
2. 增加有界群内路由与可见交接，保留负责人和用户授权，不把每句消息转成工作任务。
3. 补齐显式跨群分享与成员加入/移除上下文控制，再收敛设置和界面。

必测：

- 同一 Bot 在两个小说群同时接收请求，分别读取本群设定并写入本群产物。
- 群内 Bot A @ Bot B，发言身份、引用、接收者及真实回应可追踪；无私聊许可也不误伤已允许的群内咨询。
- 无 @ 的消息不会让全体抢答；一个阶段的产出有单一负责人。
- 异步投递重试不会重复新建同一交接工作；失败与等待如实展示。
- 咨询不会偷偷启动写稿工作；已授权工作中的咨询结果回到原工作。
- 新加入专家能查看获准的本群材料，读到的范围可查；移出后新读写被拒绝。
- 跨群联系只携带批准的内容，回应回原群，接收方不获得源群全量访问权。
- 状态广播/感谢不形成循环；到限收尾，用户能继续、停止或接管。
- A 群停止、暂停、验收或界面切换均不改变 B 群的执行生命周期。

上面保留原调研的完整验收规格，不代表全部已实现。当前增量的测试记录及手工操作见 `docs/testing/grok-peer-collaboration-acceptance.md`；跨群分享等后续项目仍待实现。
