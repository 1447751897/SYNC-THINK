## 1. 核心判断

你的理解在交互层成立：聊天消息和 Issue 评论都可以成为 @协作入口。真正需要统一的是消息后面的工作模型，而不是强制把聊天界面换成看板。

建议目标结构：

**群聊讨论 → 已确认任务卡 → 团队负责人 → 成员执行 → 结果回到同一聊天页面。**

其中“已确认任务”是显式边界：讨论消息不自动成为工作指令；已确认任务有目标、范围、约束、验收标准、来源和版本。之后的澄清和变更通过任务关联消息推进，而不是用不断增长的群聊全文反复覆盖要求。

这属于借鉴 Multica 执行模式后的产品适配，不是声称 Multica 原版已完整实现了我们的群聊流程。它的任务评论、独立 Chat、外部聊天频道各有自己的上下文路径。

## 2. Multica 的上下文不是一个全队共享大 Prompt

### 2.1 稳定运行说明：我是谁、怎么工作

daemon 将 Agent instructions、工作区说明、项目背景、平台操作规范、技能索引等组织为运行说明。不同 provider 通过自身约定的文件加载，例如 `CLAUDE.md`、`AGENTS.md`；特定适配器也有内联说明的兼容路径。

项目资源主要是索引和引用，代码库按需打开/检出，技能按领域需要读取，不是每轮自动把所有仓库、所有技能正文全塞进去。

团队负责人额外得到：协调协议、成员及其身份化 mention、角色/技能、Squad instructions。这部分是 **leader 注入**，并非所有成员共同继承的系统指令。指派与客座 @小队也区分任务状态权限。

动态用户身份、会话中断提示、连接应用等信息放在每轮消息中，而不是频繁改稳定说明，以减少 provider 提示前缀变化。这是源码设计意图，不是本轮测出的缓存收益。

### 2.3 自己的 provider 会话：我之前做过什么

普通 Issue 后续执行查找同一 **Agent + Issue** 的可续接会话，runtime 匹配才采用会话 ID。它不是“这个 Agent 去哪里都继承同一段聊天”，也不是成员继承 leader 的私有推理或工具历史。

### 2.4 持久任务记录：团队之间共享什么

团队共享的是任务描述、评论、附件、子任务关系和项目资源等可检索记录。成员通过工具读取它们，自己的完整模型会话仍单独维护。

默认工作指引要求先读任务，再扫描顶层讨论摘要，然后展开相关线程；线程读取常采用最近 30 条加分页。**30 是单次尾部读取范围，不是历史永久截断上限。** 多线程回复分别回到正确线程。

因此，上游共享上下文的核心是“持久工作记录 + 明确引用 + 按需读取 + 自己的会话续接”，而不是把全队模型历史合并或默认引入某个共享向量记忆库。

## 3. 冷启动、续接与续接失败：三种上下文模式

### 冷启动

没有有效的自身会话时，读当前任务、扫描讨论摘要、展开本轮相关线程，再按需读附件、项目资料和技能。共享记录支撑重建，而不是假装模型记得之前发生过什么。

### 有效续接

带上自身的 provider session，并发送本轮请求。服务器根据**实际采用的会话所对应的运行**计算增量：标题/描述变更，以及新评论信息。评论时间边界采用前次运行开始时刻，以覆盖上次执行期间到达的留言。

只有明确比较成功且没有变化，才允许省略相关重复读取。没有查询到增量数据，不等于“已确认零变化”。标题/描述比较也不等于对 Issue 全字段做了完整一致性证明。

### 会话不可用

daemon 会检查恢复条件，例如 provider 会话资源是否还存在。续接失败时，转回冷启动读取，并显示上下文连续性缺口。

同一运行中的特定“新会话重试”只用于识别出的续接问题，并要求尚无工具调用，避免在这个恢复路径上盲目重做已执行动作。这不是所有任务重试都具备 exactly-once 保证。

## 4. “讨论变任务”的可借鉴机制：source_context

Multica 有从已有 Issue/评论捕获上下文、生成新任务的机制。它记录来源 Issue、评论线程、锚点评论、作者、时间、修订信息、附件等。读取边界截至锚点，后续出现的新讨论不会悄悄改变已捕获的历史。

尤其值得借鉴的是权威性区分：

- 新任务的当前标题、描述与后续有效澄清，是执行依据。
- 捕获的 source_context 是只读历史背景。
- 历史材料中的命令、角色宣称、已弃用方案，不自动上升为当前执行指令。
- 快速创建任务时还明确区分“新的任务指令”和“引用的历史 JSON”。

该实现有大小护栏。例如 Agent 模式 snapshot 上限为 64 KiB，连同新指令为 72 KiB，包装后的 prompt 为 96 KiB。这些是**特定捕获流程的字节限制**，不是所有 Agent 的模型上下文窗口或全局 Token 预算。

本轮确认的是 **Issue/comment → 新任务** 的 source_context 路径。将它扩展成 **群聊 → 已确认任务** 是我们的设计工作，不能直接把上游字段当成原生群聊迁移能力。

## 5. 单个 Agent 怎样完成一次运行

### 1）事件入队

指派、评论 @、聊天、自动化或唤醒产生/合并工作。Run 记录一次执行，不等于创建一个新的永久 Agent。队列合并、权限与并发在调度层处理，不靠模型自行猜测。

### 2）runtime 领取任务

daemon 按可用容量领取；服务端在 claim 时生成配置、触发内容、上下文指针、可用会话和增量信息。准备期间还要处理 runtime 下线、目录占用等状态。

### 3）准备环境

校验 Agent/工作区身份，解析执行器，准备或复用工作目录，注入运行说明、项目/技能索引、MCP 等配置。面向平台的执行凭证限定到该 Agent/任务，目录模式和冲突策略另行处理。

不是每个 Run 都必定创建独立 worktree，也不是“不同会话”就保证物理文件互不影响。

### 4）装配本轮上下文并决定续接

把稳定说明与动态请求分开；检查实际会话可用性。有效则续接，无效则重新读任务。准备完成并获得服务端开始确认后进入执行。

### 5）调用具体 Agent 执行器

平台通过 Backend 接口调用已有执行器。例如 Claude backend 启动 CLI 进程，设置 cwd、环境、MCP 和恢复参数，再消费流式输出；其他适配器使用对应协议。

**Multica 主要负责外层调度与生命周期，具体思考—调用工具—观察结果的循环由配置的 Agent runtime 承担。** 这与自己在业务服务中为每个团队另写一套模型循环不同。

### 6）采集与控制执行

消费流式消息、工具事件、输出、用量等；处理取消、超时、无有效进展以及会话恢复。运行中追加消息取决于 provider 是否具备并声明补充输入能力；没有这项能力的路径不能宣称必然原地 steer。

### 7）结果落回工作记录

正常协议要求 Agent 把最终成果发到正确 Issue 评论线程。服务端另有条件式兜底：完成后若没有该 Agent 的评论，且有有效 output，并且不是特定静默/no_action 情形，会合成一条评论。已有进度评论也可能抑制兜底，所以它不等于成果质量验收。

保存运行结果与会话信息后，成员更新/工作流条件可以再次唤醒负责人。**Run 结束、成果提交、整个 Issue 完成是三个不同事实。**

## 6. 对 SYNC-THINK 的统一设计提案

以下均为建议的新契约，**不是已经落地的功能，也不是声称 Multica 使用相同字段名**。

### 6.1 保留聊天页，只明确消息语义

- **讨论消息**：人、Agent 在群聊里澄清与建议。@可触发讨论回复，但不因此创建工作型子任务。
- **任务卡**：把已达成的要求变成 TaskBrief，由用户确认，或通过明确的执行动作提交；记录负责团队与任务版本。
- **任务关联消息**：任务执行中的 @、澄清、变更与成员回报绑定 taskId/threadId，仍显示在原聊天页面。
- **运行事件**：排队、工具活动、失败、结果在任务卡详情中展开，聊天主流不被所有工具日志淹没。

讨论回复本身也消耗一次模型执行，所以可共用 Run 基础设施；但 purpose、可用工具和可改变的状态应不同。要保证“只讨论不派工”，应在服务端限制工作写入/派工工具，而非只写一句提示词。

原版 Squad leader 协议是协调与派工，并不是群聊里的普通发言人。因此讨论阶段 @团队时是否由 leader 仅给意见，需要我们明确适配，避免同一个 mention 在两种场景里偷偷改变意义。发送前显示实际会响应/执行的对象。

### 6.2 上下文只保留一套可解释的装配规则

建议职责拆分：

1. **TaskBrief**：目标、范围/非目标、约束、验收、负责人、版本。未确认的信息标为待澄清，不擅自编造。
2. **SourceSnapshot**：来源群聊、截止消息、引用消息/附件、作者、修订或摘要指纹；只读历史，保留权限边界。
3. **TriggerEnvelope**：本次触发者、消息、线程、原因、合并消息和精确回写位置。
4. **AgentSession**：按工作区 + Agent + 工作任务隔离；讨论会话与执行会话分开。runtime/配置变化和会话丢失要有明确处理。
5. **ContextManifest**：本轮确实注入什么、哪些仅提供引用、续接哪个会话、增量锚点、发生何种省略/失败。后续实际工具读取单独记录，不能把“允许读取”冒充“模型已经读过”。

无需每轮灌群聊全文，也不应只传一段不可追溯的 AI 摘要。推荐“已确认任务书 + 有界来源快照/索引 + 按需回读”。过大时明确提示选择/缩减或采用带引用摘要，别静默漏掉关键约束。

### 6.3 负责人和成员各自收到什么

**负责人**：自己的角色说明、团队名单/技能、协调协议、确认后的主任务、可读来源、当前工作状态与本轮事件。

**成员**：自己的角色说明、被交付的具体工作、本轮明确要求、相关任务/来源/产物引用、自己的会话。默认不复制其他成员或 leader 的完整会话，也不把整个团队 instructions 自动升级为所有成员的指令。

同一主任务中的咨询，可以通过 @关联消息完成。独立可验收的工作拆成子任务，显式带上父任务与必要材料引用；创建了可执行子任务后不要再用父任务 @重复派同一份工作。

### 6.4 举例：讨论一个登录页改造

1. 群聊先讨论“只改交互、不动鉴权协议”，过程中 @设计、@开发、@测试提出意见。
2. 确认任务卡写明目标、禁止改动的范围、验收项；捕获截至确认消息的来源。
3. @交付团队进入任务执行语境，只先启动负责人。
4. 负责人建立清楚的分工；开发拿自己的工作要求和相关设计材料，测试拿验收项、变更说明与可访问构建结果。
5. 成员成果作为任务关联记录回到聊天页；负责人据此评估下一步，不靠偷读成员私有会话。
6. 后续用户提出新要求时形成任务版本变更；已有任务不因群聊中一句无关闲聊而隐式改目标。

这是流程示例，不是上游实测输出。

## 7. 实施前的验收点

- 讨论 @可回复，但工作派发接口被讨论目的限制；明确提交后才出现工作任务。
- 同一讨论反复点击提交有幂等边界，不创建重复任务。
- 两个任务使用同一个 Agent 时，会话和结果路由不串线。
- 负责人和成员上下文不同；子任务包含必要引用而非假设自动继承。
- 冷启动、有效续接、失效续接各有测试；未知增量不等于零增量。
- 上次执行期间的评论不遗漏；多条合并输入全部有处理/回写记录。
- 历史快照内的弃用方案与当前任务冲突时，以明确有效的任务要求为准。
- 任务变更、来源材料权限变化与附件失效可追溯，不越权读取。
- 运行完成而成果缺失时，不标业务完成；进度消息不冒充最终成果。
- provider 不支持运行中补充输入时，展示真实的后续运行行为。
- 成员回报按任务事件唤醒负责人，并为自动反馈链设置可解释的去重/额度/停止条件。
- 取消、重试、工作目录复用都有真实语义；不承诺全部外部副作用只发生一次。

## 8. 与现有决定的关系、下一步范围

[ADR 0002](D:/projects/SYNC-THINK/docs/adr/0002-collaboration-workflow-delivery.md) 已明确讨论与工作流分离，这个产品意图可保留；其冻结 DAG、每轮群聊历史注入、文本 @不派发等具体执行约定需要重新决定。

[ADR 0003](D:/projects/SYNC-THINK/docs/adr/0003-user-owned-agent-definitions-and-nested-teams.md) 的团队与旧调度关系也应在实施前通过新 ADR 明确替代。保留用户聊天页和历史，不等于保留两套执行器。

建议先落地一条最小新闭环：**讨论 → 确认任务 → @团队负责人 → 一名成员 → 可验收结果 → 回到原聊天页**。验证上下文契约、状态、续接和故障恢复后再扩展多成员、阶段、自动化。

本轮只交付源码研究与方案；没有拉取或重启本项目服务，没有改动已有暂存代码、用户聊天、Agent 配置和数据库。新的自动派发策略、API 和 schema 留待实施阶段。

## 9. 最新产品收敛：一个长期目标，一个任务群

本节响应“同一小队同时写两本小说、长期任务暂停续做、额外 Agent 加入群聊”的需求。以下为 **SYNC-THINK 建议契约**，不是已实现能力，也不是 Multica 原版 UI 的描述。

### 9.1 任务群是持久容器，小队是可复用的人员配置

建议用户侧名称为 **任务群**，内部可用 `Workroom`。一个独立长期目标对应一个群：小说 A 和小说 B 各建一群，同一个小说小队加入两群。小队的身份、通用角色和技能复用；两本书的设定、历史、进度、会话和产物分开。

“一项任务一个群”指独立的主目标，不是每次 @问答、每章校对都新建群。群内拥有一项主工作、可验收子任务和讨论分支。两个目标若能独立暂停、验收且不应共享背景，默认分群。

独立目标先开新群也不意味着必须立即开工：群可以先处于讨论阶段，在同一群里确认任务书后启动执行，不再把多个主目标塞进旧的公共团队聊天室。若要从已有群的某段讨论另开任务群，使用显式来源快照，原群进度不自动搬走。

组织关系：

- Agent：可复用的身份、技能、模型和通用规则。
- Team：可复用成员、角色与负责人配置，不保存某本小说的业务进度。
- Room：该项长期工作自己的消息、任务书、资料、成员和执行策略。
- WorkItem / Thread：群内一项可追踪工作，或一个局部讨论范围。
- Run：处理本轮请求的短生命周期执行记录。
- Checkpoint / Artifact：用于长期续做的持久工作事实与版本化产物。

房间不等于一条无限长 provider 会话，Team 不等于一条全队共享运行实例。

### 9.2 同一个小说小队怎样同时写两本书

小说 A 群与小说 B 群各绑定同一个 Team 定义，但建立独立的房间参与关系。选择 A 群只读取 A 的任务书、人物设定、时间线、章节和讨论；选择 B 群同理。

同一主笔 Agent 可以在两群产生独立 Run。资源充足时可并行；达到全局 Agent/runtime 容量时排队。排队是容量问题，不应通过共用同一会话或把两本书合成一份任务解决。调度需要兼顾房间公平性，避免长任务占满全部可用槽位。

最少要隔离这些层面：

1. **消息与读取范围**：`roomId` 从存储、API、工具读取到事件回写全程携带，目标取自执行绑定而非用户最后打开的聊天。
2. **业务资料与记忆**：每群独立任务书、决策记录、摘要、人物/伏笔档案、检索索引和产物版本。通用写作风格可以显式共用；某本书的事实不自动写进 Agent 的全局记忆。
3. **provider 会话**：建议逻辑键包含工作区、房间、Agent、工作项/讨论分支和用途，另验证 runtime/provider 兼容性。一个 provider session 同时只有一个写入者；并行工作分会话。
4. **执行文件与工具范围**：产物按房间命名空间组织；必要时单独 cwd、provider 状态/记忆目录。单独文件夹只是组织方式，文件访问约束仍需工具层、权限或相应沙箱落实。
5. **调度与事件**：暂停、自动唤醒、重试、输出、预算归属和去重均绑定房间/工作项；重复或迟到事件有明确状态检查。
6. **角色与配置版本**：保留本次 Run 实际使用的 Agent、团队配置版本。修改通用角色不重写已执行记录；团队配置更新对已有房间的采用策略需显式，别静默改变另一部小说的写作规则。

这不是把 `roomId` 加进 prompt 就完成隔离。数据库查询、工具、索引、执行目录、外部资源和回调都需要同一条范围边界。若允许任意全盘 shell 或共用外部账号资源，就应展示真实能力边界，不把 UI 分群当成强访问隔离。

### 9.3 长任务续做靠检查点，不靠模型进程常驻

小说这类长任务建议分成有界执行单元：设定、某章草稿、校对、修订等。每个单元完成后保存工作状态和产物，团队再决定下一步，不以“同一个模型连续运行数周”作为可靠性基础。

每个工作检查点至少有：

- 当前任务书版本、已确认决定与仍待澄清项；
- 已完成/待审核/未完成的工作项，以及具体下一步；
- 正文、设定等产物 ID、修订版本和保存位置；
- 活动 Run、待处理请求、失败或中断原因；
- 已知文件变更和可能完成的外部动作，供恢复时核对；
- 可用会话 ID、上下文来源与读取游标，作为续接优化而非唯一真相。

小说专用工作资料可包含人物档案、世界观/时间线、伏笔清单、章节梗概、定稿正文和待审核草稿；资料更新需有版本和出处，模型摘要不自动升级为已确认设定。恢复某章时按需读取相邻章节和相关设定，而非把全书都塞入窗口。

三种操作应分开：

- **切换到别的群**：只改变前台页面，运行默认照常进行，进展记为对应群的未读。
- **暂停工作**：阻止新的工作型执行和自动推进；对活动 Run 请求保存/停止，进入 `pausing`，待终止被确认后再显示 `paused`。仍可讨论或查看资料，但受讨论模式工具限制。
- **继续工作**：读取当前任务版本、检查点和真实产物；核对是否有运行仍在活动、未提交改动或未确认外部动作；能续接则续接，否则重新构建上下文，再启动下一次 Run。

暂停期间到达的结果仍记录，但不触发下一批工作。恢复时核对并按幂等事件处理待办输入，不重放整段历史。暂停不是回滚；已发生的文件修改或外部动作不会自动撤销。资源没有真正停下时保持“正在暂停/停止异常”，别假装已保存了完美检查点。

系统重启后从持久记录恢复房间状态、运行归属和待办事件；先核实外部执行器状态，防止同一工作被重复启动。

### 9.4 群成员可以是小队，也可以是额外 Agent

一个任务群可以包含负责小队、协作小队、独立 Agent 和人。建议每项主工作有一个默认负责团队或主负责人；额外成员是可调用参与者，不自动获得协调权，也不额外增加一层永久总协调 Agent。

加入 Agent 的默认含义：

1. 建立房间成员/参与关系，按权限可读取本群历史和资料；默认包含加入前历史，若房间另有限制则明确显示范围。
2. 没有 Run 因“加入”自动启动；不广播唤醒全队。
3. 首次被 @时装配当前任务简报、本轮请求、相关历史索引/摘要和资料引用，必要时回读原文。
4. 后续会话属于此群和该工作范围，不继承它在其他小说群的工作记忆。
5. 房间阅读资格不等于全工作区文件或全部外部连接的权限；发送给实际模型前明确其执行环境与能力范围。

加入的是“这个群”，不必永久修改小说小队定义。跨群引用材料需要显式选择、来源记录和读取权限，不自动合并两群全文。

同一 Agent 既随小队加入又被单独添加时，保留参与来源，但同一次 @操作默认按 Agent 身份去重。只有用户明确创建不同工作项/角色执行，才产生额外工作，而不是重复点名隐式执行两次。

移出成员应先撤销后续领取与读取资格，处理活动 Run，再完成移除；已发送给 provider 的内容不会因移出而自动消失。保留历史作者和产物记录，不从聊天历史抹除贡献。

### 9.5 @小问答和 @小工作无需都变成长流程

建议由输入框/消息卡呈现明确、轻量的意图：

- **咨询**：`@历史顾问 这个称谓符合时代吗？` → 读取本群相关片段并回复；创建对话 Run，不自动派发团队工作、不修改小说正文。
- **小工作**：`@编辑 检查这段的视角一致性` → 在群内生成轻量工作记录、执行、回传建议；不新建群。若涉及修改定稿，遵循对应版本与确认规则。
- **推进主工作**：`@小说小队 按已确认大纲写下一章` → 进入该群任务执行语境，先由负责小队 leader 协调。

无需每条咨询都弹出大型任务表单。意图可以从明确指令生成可见预览；有歧义时默认不产生工作写入，提供轻量确认。服务端校验实际可用工具，别把“模型口头说只回答”当权限机制。

群内多条并行讨论和子任务使用回复分支/工作卡关联，执行中途切换页面不改变结果去向。所有成员都具备本群适用资料的访问资格，但每次执行只装配必要上下文；“看得到”和“本轮实际读过”分开记录。

### 9.6 推荐的用户界面

沿用聊天页主体，补上目标范围，不照搬一个重型项目管理产品：

- 左侧：独立任务群列表，可看到小说 A、小说 B 各自状态与未读。
- 顶部：群名、主目标、默认负责团队、工作状态、暂停/继续。
- 中间：讨论、任务卡、成员成果；支持局部回复分支。
- 右侧或抽屉：任务进度、资料/产物、成员、上下文与运行记录。
- 新建入口：新任务群 → 简要目标 → 选团队/Agent → 先讨论或明确启动。

从旧群“拆为新任务群”时，只带上明确选择的任务、来源材料和资料引用；保留来源链接，不复制原群所有运行、所有成员记忆或所有文件。具体旧数据迁移需独立设计。

### 9.7 新增验收场景与 ADR 边界

- 同一 Team、同一主笔在 A/B 两群执行：日志、会话、正文、记忆索引和未读都归正确群。
- 容量不足时公平排队；不为并发复用同一 provider session。
- 暂停 A 不暂停 B；打开 B 不隐式取消 A。
- A 暂停期间结果到达：记录结果，但不自动推进 A 的下一阶段。
- 重启或会话丢失后继续 A：读取已保存版本与真实文件，不盲目重做已完成章节。
- 给 A 加顾问：不修改 Team 定义、不增加 B 群成员、不立刻运行；被 @后可读 A 加入前允许的历史。
- 咨询只产生回复；小工作有轻量结果记录；两者都不另建群。
- 两个成员修改同一正文版本：检测冲突，采用产物锁或版本条件更新，不静默覆盖。
- 同一次 @重复指向一个 Agent：默认一次响应；回复绑定原群/原分支。
- 角色记忆、文件工具与外部连接都经过范围测试；不把对话隔离误当作所有外部副作用隔离。

这延续 ADR 0003 的“用户拥有 Agent 定义、群里可以组合小队和普通 Agent”的产品意图，但不保留其固定 DAG、旧命名空间和旧调度器作为前提。新会话键、成员去重、工作检查点和暂停状态应在实施时由替代 ADR 明确。当前未修改现有 ADR 或运行实现。
