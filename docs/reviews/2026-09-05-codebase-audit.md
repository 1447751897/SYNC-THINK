## 3. P0：审批恢复仍走全量历史扫描

**证据级别：源码确认；未在运行中的大库上主动触发冷扫描。**

- `apps/runtime/src/runtime.ts:27727` 的 `durableChatToolApprovalStates()` 首次调用从 sequence=0 开始，循环 `listEventPage()` 直到最新游标。
- 每页读出并解析全部事件后，`rememberDurableChatToolApprovalEvent()` 才过滤两类审批事件。这是分批处理全库，不是按审批条件读取。
- `apps/desktop/src/renderer/shell/ChatView.tsx:3013` 在打开会话及重连时查询待审批。Runtime 重启会清空 hydration 标志，因此冷恢复之后的一次普通 UI 查询可能触发上述重工作。
- 当前库文件 17,007,321,088 字节（17.01 GB / 15.84 GiB），最新 sequence=1,993,552。sequence 是游标，不应直接当作现存事件行数。

**用户影响：** Runtime 冷恢复后，打开对话/审批可能长时间等待；同步恢复循环还会占用 Runtime 事件循环。仅重启 Desktop 不一定触发，因此偶发且难用小夹具察觉。

**审批语义尚未完全收口：**

- 当前已具备耐久审批事件和幂等决定，绝非“审批完全没有持久化”。现有恢复测试已通过。
- `runtime.ts:27816` 会把有请求、无决定、但没有内存 waiter 的记录再次列为待审批。
- `runtime.ts:27601` 收到该孤儿审批的操作时才写入 `deny / stale-approval`；即使输入是批准，旧执行上下文也不会因此继续。
- UI 对已知终态 Run 有过滤，但应由 Runtime 对“有效、已恢复、已过期”给出权威状态，而不是依赖客户端恰好拿到了终态历史。

**建议：**

1. 区分聊天工具审批与现有 orchestration `approval_request` 的领域语义，复用或新增专用读模型；按 thread/run/state 查询。
2. 首次迁移单独记录游标和版本，后台有界执行；在线查询不承担全库回填。
3. 明确 Desktop 重连继续等待、Runtime 重启重建新审批或持久标记失效的协议；不尝试持久化 Promise。
4. 明确到期原因、操作可用性和重新执行入口，保留幂等和审计证据。

**验收：** 无关事件增加不使待审批读取线性增长；读路径有索引证据；冷恢复、批准、拒绝、重复点击、取消与重连均有集成测试；没有 waiter 的旧卡片不再表现成可继续的正常审批。

## 4. P0：任务和执行过程读取仍携带巨大历史状态

**证据级别：本机实测 + 源码确认。**

### 4.1 会话初次读取任务清单约 1.1 秒

- `packages/storage/src/runtime-state-store.ts:256` 的 `listTaskPlanEvents()` 已按 task 索引收敛，但仍在任务事件上重复 `json_extract` / 工具名匹配，并返回命中事件的完整 payload。
- `apps/runtime/src/runtime.ts:8693` 每次初始 `conversation.listMessages` 会执行该查询，再归约原生任务状态。
- 选定真实历史任务连续 3 次：1082.66 / 1079.53 / 1116.69 ms；命中 28 条，完整事件数组序列化后约 14.04 MB。
- 大记录的任务参数只有数百字节，但同一 payload 内的 `run` 快照约 4.65 MB。
- 14.04 MB 是存储层中间数据量，不是最终任务卡 IPC 响应大小。

### 4.2 一个历史执行过程约 0.3 秒

- `apps/runtime/src/runtime.ts:9064` 的 getRunProcess 全量读取单个 Run 的事件，再在内存归约；没有独立的完成态过程快照读取路径。
- 大样本 83 条事件：读与 JSON 解析为 268.95 / 305.61 / 316.45 ms；投影另需 6.63–12.54 ms；最终过程视图仅 53,776 字节。
- 小样本 25 条事件：读与解析 1.13–1.22 ms，最终视图 701 字节。这说明主要差别是 payload，而非简单事件条数。
- `ChatView.tsx:3376` 对已加载的历史助手 Run 逐个发起过程请求，没有独立并发队列；失败后退避上限 8 秒，但没有最大尝试次数和错误分类。

### 4.3 数据增长的原因不能归结为“垃圾文件”

- 当前 freelist_count=0：没有可直接通过空闲页回收获得大幅缩小的证据。本轮不运行 VACUUM。
- 末尾 100 条中，一个 fallback 事件的 `run` 占约 4.65 MB，其中 `assistantTimeline` 约 2.33 MB、`kernelToolEvents` 约 2.32 MB，存在双份过程内容。
- `apps/runtime/src/demo-run.ts:942` 的 `serializeDemoRun()` 去掉 Skill/context 等展开字段，但仍保留 timeline 和工具历史。
- `apps/runtime/src/runtime.ts:20090` 的 Native 非终态持久投影、`:25297` 的 fallback 仍会带上 run 快照。
- 外部内核的当前 `provider.usage` 已是精简字段（`:2257`、`:23784`），不应把历史大 usage 行误说成所有新 usage 仍有此问题。
- sidecar 已实现，但 `apps/runtime/src/main.ts:52` 默认需要环境开关，`persistence.ts:321` 当前仅覆盖 `context.packet.built`。只打开该开关并不能解决上述 run 快照复制。
- 这些样本确认了成本和膨胀机制，但不代表已证明整个 17GB 的逐表成因。

**建议：**

1. 原生任务事件仍是唯一事实来源，增加 task-plan 物化读模型及版本/游标；不是再加一套模型需要主动写入的任务系统。
2. 完成态 Run 过程视图持久化或按 event-version 缓存；工具大结果单独寻址，列表只读摘要，详情按需加载。
3. 将“可恢复 checkpoint”与“可展示事件”拆开；正文/工具输出使用引用，逐步去掉重复 run 快照，不牺牲崩溃恢复所需数据。
4. 历史迁移先统计、备份、校验、dry-run，再有界迁移；最后才评估维护窗口内的物理回收。
5. 历史过程读取按可见性调度、限制并发；永久错误停止自动重试并展示可手动恢复入口。

**验收目标（待实施测量）：** 同样本任务和过程读取暖态低于 100 ms；在线查询不解析不相关的大输出；查询优化不改变任务结果、工具顺序、正文或 Token 统计；迁移支持校验和回退。

## 12. 实施记录：冷恢复 Worker 与执行过程读取（2026-09-05）

### 实现结果

1. 任务冷恢复拆成只读事务捕获与短事务安装：归约期间其他连接可提交事件；安装时校验 source cursor，不把竞态产生的旧快照保存成当前状态。生产 Runtime 的 `conversation.listMessages` 只在快照未命中时异步请求 Worker；任务归约不再占用主线程或长期持有写锁。
2. 修正冷筛选 SQL 的重复 JSON 解析：materialized 工具元数据只提取一次，再关联原生请求与未携带工具名的结果。选中行剔除重复 run 快照；非任务工具的大结果不返回给任务归约器。
3. 新增执行过程专用事件读取，保留工具事实、文件完整内容、Token/occupancy 与模型元数据，移除重复运行快照并跳过不参与投影的事件。Worker 在一致只读事务中捕获 Run 游标与过程视图；主线程按 event cursor 使用最多 32 个 Run / 16 MiB 的缓存，后续事件会使旧缓存失效。
4. 每个 Runtime 延迟创建一个只读历史 Worker，最多 32 个去重请求，30 秒超时，空闲 30 秒释放；关闭或 Worker 失败会拒绝在途请求，超时后支持重建。复用现有 Node/SQLite/tsx 能力，没有引入新的基础设施或依赖。
5. 派生任务快照写失败时仍返回已读取的源快照，并以每分钟至多一次的固定文本记录诊断；不让可选缓存失败使整页历史消失。Runtime 停止时关闭 reader，Worker 配置沿用父 Runtime 的 sidecar 路径。

## 14. 实施记录：导航几何缓存与长会话重复渲染（2026-09-05）

### 根因与实现

1. 原导航在每次滚动重新查询所有消息节点、读取矩形并线性查找当前轮次。现在消息位置首次捕获后缓存；ResizeObserver 提供行高增量，通过前缀和树更新后续位置，按阅读焦点二分查找。仅结构、宽度或非消息间隙变化才整体重建，文字摘要变化不重新订阅观察器。隐藏页面也观察滚动容器，显示后自动建缓存。

### 17.1 根因与实现

## 18.19 真实审批、独立进程失效与关闭收尾（2026-09-06）

### 定位与最小修复

- 外部内核权限桥在 `persistProjectedEvent` 失败后原先吞掉错误，仍登记内存 waiter；持久记录缺失时前端没有可恢复的审批卡，原生工具却继续等待。现在仅拒绝本次原生权限请求并返回“审批请求登记失败，本次操作未获批准。”，不安装 waiter，不扩大权限、不自动重试。
- 实际 Claude 审批验收中，Runtime 关闭数据库后仍有 Native run 的 finally 调用 `maybeStartPendingGoalTurn`，出现 database-not-open。原 stop 只等待外部会话队列，不拥有所有 Native/外部执行 Promise。现在统一跟踪整个内核运行，关闭标志先置位，取消后等待完整收尾，再释放持久会话；关闭期间禁止新内核运行和目标续轮读库。
