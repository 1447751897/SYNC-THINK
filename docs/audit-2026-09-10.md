## 一、性能问题（按影响排序）

### P0-1 能力页每 30 秒强制磁盘重扫 + 4 个并发 IPC ✅ 已修复

`KeepAliveLayer` 现通过可见性上下文向被冻结的保活子树发布激活状态；`AbilityCenterPage` 只在首次进入和重新进入时调用 `loadLocalSkills`，不再注册 30 秒 interval。隐藏页面不再持续发起 `skillLocalScan({ refresh: true })` 和四类目录读取，DOM 与滚动位置仍由保活层保存。

回归测试同时验证：不存在 30,000ms interval、隐藏期间扫描次数不增加、重新进入触发一次刷新，且已安装列表节点与滚动位置不变。

单次扫描也已移出同步分发路径：启用插件来源发现、目录递归、文件状态/内容读取与真实路径去重均使用异步文件 API；`skill.local.scan` 作为 Runtime 后台任务执行。扫描刷新用代次与 in-flight Promise 协调，并发调用共享当前工作，扫描期间到达的新变更会追加一代，避免旧结果覆盖。

文件 watcher 继续以 300ms debounce 作为变化信号，刷新任务纳入 Runtime 关闭等待；来源快照由扫描响应和 watcher 共用。40 文件行为回归确认 timer 可在扫描结束前运行，固定轮询和单次事件循环阻塞两部分风险均已消除。

Watcher 的目录去重、活动状态与 cleanup 生命周期现已进一步收敛到 `LocalSkillWatchRegistry`；Runtime 只保留来源选择和变化后的刷新/事件编排。注册表保证批量停止时先清空所有权，并在单个 cleanup 失败时继续释放其余 watcher。

刷新 generation、等待者与尾随加载算法也已提升到 Shared `RefreshCoordinator`，由 Desktop 与 Runtime 共用；两个宿主通过显式策略保留各自既有启动和失败语义，Desktop 本地重复实现及 Runtime 三份协调状态已删除。

### P0-2 同一份 catalog 被 6 处独立拉取，无共享缓存 ✅ 已修复

`skill-catalog-loader.ts` 与 `mcp-catalog-loader.ts` 分别统一 Skill 和 MCP 元数据读取：

- 所有普通请求统一为 500 条，并按 Runtime bridge 实例与全局/工作区作用域分区；
- 同作用域并发请求共享同一个 Promise，成功结果复用，失败不缓存；
- 能力写操作显式失效全部作用域；失效时仍在途的旧请求会自动重读，避免旧结果回写；
- Shell 快照、能力页重新进入和用户手动刷新仍保留强制读取语义；
- AST 架构门禁禁止 Renderer Shell 组件绕过加载器直接调用 `listSkills`。
- MCP 普通请求统一为 100 条，按 Runtime bridge 实例复用；Ability Center、Agent Library、Composer MCP 菜单和设置连接页共享并发请求与成功快照；
- MCP 注册、删除、启停和工具刷新显式失效，失效前在途响应按新代次重读；AST 门禁同样禁止组件直接调用 `listMcpServers`。

Skill 共享加载器 6 项及六个消费者相关 UI 189 项回归通过；MCP 共享加载器及四个消费者定向 251 项通过。生产源码检索仅对应加载器保留直接 `listSkills` / `listMcpServers` 调用。

**已消除影响**：斜杠菜单、回合 Skill 控制、智能体绑定、Agent Library、设置连接页和能力页不再各自重复发起同一目录全量读取；页面状态与目录缓存职责保持分离。

### P0-3 「使用统计」每次进入都重新加载 ✅ 已修复

根因链（三条全部核实）：

1. `ModelSettings.tsx:5084-5086` —— `useEffect(() => { void load(); }, [load, reloadToken])`，**挂载即加载**，无模块级缓存
2. `KeepAliveLayer.tsx:11-13` —— `const visited = useRef(props.active)`，**实例销毁即丢失已访问状态**
3. `ShellApp.tsx:4149 / 5821` —— `SettingsModal` 用 `<Dialog.Root open={settingsOpen}>` + `<Dialog.Portal>`，**没有 `forceMount`** → 关闭设置即卸载整棵 `SettingsPage` → 所有 `KeepAliveLayer` 的 `visited` 重置

**已落地**：复用并泛化 `provider-usage-summary` 的 5 分钟 TTL + in-flight 边界，按查询时间范围隔离缓存；`UsageSettings` 可同步读取新鲜快照作为重挂载初值，因此关闭并重开设置不会重复请求或闪回加载态。手动刷新与价格保存仍强制请求，失败不会覆盖成功快照。

没有采用 `Dialog.Portal forceMount`：它会让隐藏模态的焦点、事件和整棵设置页状态一起常驻，解决一项统计数据复用却扩大 UI 生命周期耦合。定向回归覆盖同范围重挂载只请求一次、范围隔离、TTL 过期、强制刷新和 ChatView 既有 30 天汇总，共 75 项通过。

### P1-1 `refresh()` 全量重拉 + 全量序列化写盘，约 20 处调用 ✅ 已修复

`ShellApp` 的六目录读取继续原子提交；独立 `RefreshCoordinator` 已合并同一任务的重复请求，并把活动读取期间的新请求收敛为一轮尾随刷新。这样不会以修改前的 in-flight 结果满足修改后的调用者，也不会让约 20 个入口并行制造刷新风暴。

启动快照已改为 250ms 尾随写入，只序列化最后一份成功数据，Shell 卸载时冲刷；连续标题更新不再逐次同步写 localStorage。协调器、快照和 Shell 接线回归共 86 项通过。

`conversation.list` 现支持 1–200 条的稳定 keyset 分页；Shell 通过独立加载器每页读取 100 条并汇总完整目录，单个 Runtime Frame / IPC 响应不再随历史总量无限增长。跨页按 ID 去重并拒绝重复游标，旧无分页调用保持兼容。

**已消除影响**：刷新风暴、逐次全量 localStorage 写入和单帧无界会话载荷均已消除。为了不改变侧栏搜索、归档、跨工作区活动和深链行为，Shell 仍聚合全部页，因此一次完整刷新总工作量保持 O(n)；后续按需 UI 加载只在真实性能指标需要时单独设计。

### P1-3 后台空转轮询 ✅ 已修复

`useVisiblePolling` 现在统一三处 Renderer 周期读取：文档隐藏或 KeepAlive 页面非激活时停止调度，重新可见时立即刷新；下一次定时只在当前 Promise 完成后创建，因此不会重叠；失败按 2 倍周期退避到 8 倍上限，成功后恢复正常周期。所有消费者共享一条 `visibilitychange` 监听。

### P1-4 `usage.summary` 后端平方级计算 + 超大载荷 ✅ 已修复

Runtime 现在单次遍历请求即可同时完成显示字段装饰、总量累计和 provider/model 费用索引，汇总行通过索引读取费用，不再在每一行执行 `requests.filter`；响应投影复杂度收敛为 O(rows + requests)。

## 二、重复功能实现

### R-1 执行过程投影两份 296 行近似拷贝 ✅ 已修复

Renderer 的 `execution-process.ts` 及两份封闭测试已删除，共移除 1,932 行。执行事件现在只由 Runtime `run-process-view` 投影为 Protocol `RunProcessView`；Renderer 直接消费该对象，不再解释原始 Event。

### R-2 浏览器 payload 解析器成对重复 ✅ 已修复

Browser Profile、Recording、Workflow 共 18 个解析规则已集中到浏览器安全的 `@sync-think/protocol/browser-payloads` 子路径。Runtime 三个文件只做别名导出，Desktop 三个文件只把共享解析失败转换为既有命令错误；字段白名单、长度、URL、控制字符和变量规则不再成对维护。

六个宿主实现由 864 行缩为 178 行适配器，共享真源 364 行，生产解析代码净减少 322 行。新增架构门禁禁止适配器重新声明校验函数；Workflow 变量名 512、值 4000 字符的 Runtime 上限同步成为 Desktop 预检边界。

### R-3 Telegram 能力两套实现同时存活 ✅ 已修复

### B-1 `ActivityCenterPage` refresh 无 requestId 守卫 ✅ 已修复
